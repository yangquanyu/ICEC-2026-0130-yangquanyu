# 案例 01：解析器漏掉列表第一条通知（19/20）

## 问题现象

notice_watcher v1.1.0 加装"过滤导航/外链 + 提取日期"后重跑，遥测日志显示 `items_total=19`，
而页面实际有 20 条通知链接。缺的恰好是列表第一条（2026-11-16 困难补助公示）。

## 提问方式

向 AI 描述：预期 20 条、实际 19 条、缺的是第一条；附上 `LinkParser` 类的完整代码
和页面的一段真实 HTML（含面包屑导航 + 第一条 `<li>`）。要求：列出可能的根因假设和各自的验证方法。

## AI 诊断路径

1. 假设一：第一条被过滤规则误杀（域名/自链接判断）→ 验证：打印每条链接的过滤原因；
2. 假设二：第一条根本没进解析结果 → 验证：打印 `parser.items` 原始输出；
3. 实测走假设二：`items` 里第一条是 ("首页", "/html/", ...)，真正的通知不在其中；
4. AI 进一步指出：面包屑里的 `<a>` 不在任何 `<li>` 内，而解析器只在 `</li>` 时收尾链接，
   导致面包屑的链接状态一直悬挂，把后面第一条通知的 `<a>` 整个吞掉。

## 根因

`LinkParser.handle_starttag` 只在 `self._href is None` 时才开始新链接。面包屑导航的 `<a>`
设置了 `_href` 后永远等不到 `</li>` 来收尾，状态一直占用；随后列表第一条通知的 `<a>`
被"已占用"判断跳过，其标题和日期全部并入了面包屑那条的尾部文本。

## 修复

在每个 `<li>` 开始时重置链接状态（丢弃任何悬挂的 `<a>`）：

```python
def handle_starttag(self, tag, attrs):
    t = tag.lower()
    if t == "li":
        self._href = None
        self._title_parts = []
        self._tail_parts = []
        self._title_done = False
    elif t == "a" and self._href is None:
        ...
```

## 验证

清空 `state/seen.json` 重建基线后重跑：识别 20 条，与 `grep -oE 'href="/html/tzgg/[0-9]+\.html"' | sort -u | wc -l`
的页面实际链接数一致；紧接着第二次运行 `items_new=0`，去重正常。两个提交（c0563a5 问题现场、
81ab740 修复）在 git 历史中相邻，面试可直接追溯。

## 复盘

- 教训：解析器对"标签嵌套假设"很脆弱，HTML 里任何预期外的结构（面包屑、广告位）都可能污染状态；
- 方法沉淀：先用 `grep` 数出页面真实链接数作为基准，再对比程序输出，差距一眼可见；
-  AI 的价值在于把"第一条去哪了"这类模糊现象快速收敛到 2~3 个可验证假设，但每个假设都必须自己跑数据验证。
